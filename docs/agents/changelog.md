# Changelog and releases

Use this process when a pull request will merge into `main`, when correcting published release documentation, or when verifying a publication.

Releases are automated with [release-please](https://github.com/googleapis/release-please): it generates the version bump, the `CHANGELOG.md` entry, the `v<version>` tag, the GitHub Release, and the npm publication. The human gate is the review of the release PR that release-please opens. Do not hand-write `CHANGELOG.md`, versions, or tags.

## How a release happens

1. Work merges into `develop` as Conventional Commits per [commit-policy.md](commit-policy.md). The commit type decides the bump class: `feat` is minor, `fix` is patch, and before `1.0.0` a breaking change also bumps minor, per [git-workflow.md](git-workflow.md). `release-please-config.json` sets `bump-minor-pre-major` so the generated version follows that rule.
2. A release branch merges into `main` per [git-workflow.md](git-workflow.md).
3. On the merge, the release-please workflow opens a release PR on `main` carrying the next version and the generated changelog entry covering every commit since the previous tag.
4. Review the release PR: the version fits the changes (the pre-1.0 rule in [git-workflow.md](git-workflow.md)) and the entry is accurate and understandable to an operator or contributor. If a generated line is inaccurate, fix that line in the release PR before merging it; if a change should not ship at all, take it off the release branch and let release-please regenerate.
5. Merging the release PR runs the release workflow: the annotated `v<version>` tag on the release merge commit, the GitHub Release with the entry as its body, and `npm publish` via OIDC trusted publishing.

The release is ready only when the release PR is merged and every publication check below passes.

## Rules

- Root `CHANGELOG.md` on `main` is the canonical release record and is generated by release-please. A GitHub Release copies the matching entry; it is not a separate editorial source.
- Feature and bug-fix work never touches `CHANGELOG.md`. Only the release PR changes it.
- The bump class is decided by commit types, so a change that needs a different bump gets the right Conventional Commit type before it merges into `develop`, not in the release PR.
- Never edit a published changelog entry, tag, or GitHub Release. Correct a small error with a note in the next release's entry; prepare a patch release for an error that could cause an operator or contributor to act incorrectly.

## Verify a publication

After the release PR merges, check:

- the `v<version>` tag exists on the release merge commit;
- the GitHub Release body matches the changelog entry;
- the npm package is published at that version;
- the tag, the GitHub Release, and `CHANGELOG.md` all name the same version.

A publication failure blocks the next pull request into `main` until the records match.
